## 3. The design, contract by contract

**S1 — the kind profile `document-set`** in `lib/py/bbx/config.py` KINDS,
third profile (D9's "revisit when a third kind exists" comes due: the
default kind stays `frame-driven` for bbh's configs). Keys: `instrument_word`
"extractor"; `tier.patterns` empty (nothing reaches an instrument: the kind is
PORTABLE — sh + python3 over files, so its gates go in `gates/portable.txt`
and its fixture runs on R21's host with no lineage tree); `[suite]`:
`scenario_ext = "claims"` (R32), `driver = "docset"`, `driver_home` the
kind-blind `$BBX_HOME/drivers` (D28, now populated), `runs_per_replay` 2
(D29), `hermetic_unset` = the kind's driver family (`DOCSET_FORMS`,
`DOCSET_NONDET`, `DOCSET_VIEW`), `mask_default` none (D26), `hash_cmd` the
kind-blind python (D27), `input_env` `BBX_INPUT`; `[fingerprint]` the
kind-blind `file-sha1` with `file_pattern = "{set}.tsv"` (D16): the program
key is the artifact's SHA-1 and the whole-set key is the hash over the
artifact AND every document beside it — the identity CLAUDE.md §3.4 asks for
(computed from the files, never from what a document says of itself),
with one measured limit: the document set must be flat in the artifact's
directory (`dir_sha1` is not recursive; a nested tree is a stated
NOT-ASSERTED of this slice, S4 or later if a consumer needs it); no
`[thresholds]` table (a temporal comparator under this profile is REFUSED —
S2's rule, D23); `[expectations].kinds` = the kind-blind three plus the four
below.

**S2 — identity.** The registry row is written at freeze time on the
WHOLE-SET key (the shape bbh's `build-a` / `build-b` use): a changed
document or a changed artifact is an unregistered identity and FAILS loudly
before any claim is read `[BBH-67]`. The scenario (a claim set) is not part
of the identity — it is the input, as a replay is.

**S4 — views.** Two, declared in the profile and named by every reader:
`text` (the documents, from which claims are QUOTED) and `artifact` (the
table, from which values are DERIVED). The driver reads both; a claim's log
token records which view each side came from. `DOCSET_VIEW` selects the
artifact view when a set carries more than one artifact (S4's question;
one artifact in S3, the variable REFUSED if set — D3).

**D1–D5 — the driver `drivers/docset.sh`** (sh, calling
`lib/py/bbx/docset.py`): `docset.sh <set> <claims-file> <out.log> [sandbox]`,
bbh's four arguments (D1). `<set>` names the artifact (`<set>.tsv` on the
search path `DOCSET_PATH`, the driver's own variable, `[suite].rompath_env`);
the claim set says which documents, which sentence forms and which view. The
out file is removed before the run (D5). Exits: 0 the log is complete
(`END <n>`); 1 the artifact or a named document cannot be read (DISCARDED);
3 `REFUSED: drivers/docset.sh cannot honour <what> (<why>)` — a sentence form
the extractor does not implement, `DOCSET_VIEW` naming a second artifact, any
of the frame-driven family (`MASK_RANGES`, `POKES`, …) present in the
environment. No exit 2 (the kind has no guard). The driver family is
declared in the profile and scrubbed by the suite (D2, `[BBH-35]`).

**The claim set** (`<scenario>.claims`, the scenario file — R32): a TOML
subset file (the reader BBX already trusts, R24's argument): `documents =
["a.md", "b.md"]`, `forms = ["has", "of-is", "row"]`, `view = "artifact"`,
and — written by the fixture generator, or by a consumer at freeze time — the
`[unbindable]` table listing every claim that is declared present but NOT
bound, with its reason (`absence` — BBX-7, SMS "describing an absence stays
unchecked"; `no-source` — the number appears in no artifact; `paraphrase` —
bound to the literal fact it summarises, R33). Nothing in the claim set
states an expected VALUE (§3.4: the expectation lives in the expectation
set, anchored on the artifact, never in the input).

**O1 — the observation grammar**, the point-indexed log logfmt already reads
(R31): one line per claim, `<index> <token>`, then `END <n>`; `<index>` is
the claim's position in the extraction order (document order in the claim
set, then line, then form — deterministic by construction, and the claim set
is the map from index to `(document, line, form)`); `<token>` is one
space-free field `<status>:<sha1-of-quoted>:<sha1-of-derived>` where
`<status>` is one of the closed vocabulary `BOUND | PARAPHRASE | UNBINDABLE |
STALE | MISMATCH` (R33). The hashes make the token compare as a token (O1:
"tokens are compared as tokens and never interpreted") while a triage can
re-derive both sides from the index. `END <n>` with `n` = claims seen,
UNBINDABLE ones included — the denominator is in the log.

**O3 — one reader.** `logfmt.frames()` unchanged (it is bbh's, F17); the
doc-set tools read the log through it and split the token by `:` in ONE
place (`docset.py`), by field name.

**O5 — input integrity.** The grammar has no header lines (bbh's has none),
so what the driver actually read is recorded inside the tokens: the
`<sha1-of-quoted>` half of every token changes when a document is edited
under the driver, and the suite's identity (S2) refuses a changed input
before the run. The assertion's must-fire is the edited-document control.

**O6 — twice.** Every claim set runs twice through the suite (D29); the
driver's `DOCSET_NONDET=1` mixes the clock into every token — the NONDETERMINISTIC
control of the kind (bbh's `FAKE_NONDET` analogue).

**E1 — the kinds** added to the `document-set` profile's table, each a file
under `<expected_dir>/<expset>/<scenario>.<kind>`:

| kind (extension) | family | disposition | what it freezes | spec line (`<class> <baseset> <args>`, R23) |
|---|---|---|---|---|
| `truth` | `exact` | EVAL | the expected token per claim index — a log in the O1 grammar written by the fixture generator from the DESIGN (fixture class), or by a consumer from its reference | `exact <baseset>` — the pairing is `logs/<scenario>.log` under the baseset, compared line by line, the first differing INDEX named (never `cmp`'s byte offset: BBX-4's spirit, a triage needs the claim) |
| `claims` | `set` | EVAL | the claim INVENTORY: the multiset of `(document, line, form)` the driver bound or listed, compared both ways (E5, BBX-17) | `multiset <baseset> inventory`, then the frozen rows in the same file, one per claim, `<document>\t<line>\t<form>\t<status>` (one file per expectation, as bbh's `.masked` carries its spec) |
| `covered` | `set` | EVAL | the COVERED set — the multiset of claims whose status is `BOUND` or `PARAPHRASE` — shrink-only (R33): a frozen row not reached FAILS naming it; growth is printed as a NOTE and re-freezes under `--freeze`; a duplicate row FAILS (multiset) | `multiset <baseset> shrink-only` then the rows |
| `schema` | `schema` | EVAL | the artifact's SHAPE, checked BEFORE any value is trusted (R34): header names in order, one type per column from `int | hex | str | nonempty`, the row count as `>= n` or `= n` | `schema <baseset> tsv` then `column <name> <type>` lines and one `rows <op> <n>` line |

A scenario may carry several of these (a claim set has a truth, an
inventory, a covered set; the artifact has a schema): every kind present is
its own PAIRING with its own verdict line and its own kept-run row keyed
`(scenario, kind)` (R32; D30's `results.tsv` already carries `kind`). Under
the `frame-driven` profile the loop is bbh's precedence verbatim — one kind
per scenario, `masked` > `diverge` > `sha1` — so F12 diffs empty; the
document-set loop is the kinds table's order. `.masked` under the
`document-set` profile is UNKNOWN-KIND (R23's detector, a control below).
`.sha1` stays available and stays `self` class (E4).

**E2, E3.** `.pending` and NO-EXPECTATION stay FAILUREs with bbh's text. The
fixture's register `fixture/docset/expected/PROVENANCE.toml` (D31): every
`truth`, `claims`, `covered` and `schema` row is class `fixture` — and the
screen counts them as "not evidence about a real subject" (R24), which is
the true sentence about a fixture; the registry row is `registry`.

**C1, C2 — two new families under one `compare.sh`** (R23): `set)` →
`compare_set <expdir> <name> <spec> <log>` calling
`lib/py/bbx/compare_set.py` (multiset both ways over rows; modes `inventory`
and `shrink-only`; a duplicate is named as hand-editing); `schema)` →
`compare_schema` calling `lib/py/bbx/compare_schema.py` (the artifact is
resolved from the run's `DOCSET_PATH`, the shape checked, the FIRST violation
named — column, type, row); `exact)` → `compare_exact` calling
`lib/py/bbx/compare_exact.py` (the truth log against the run log, by index).
Each prints ONE verdict line in BBX's own text, frozen from the first green
by the family's gate (C4: "the printed verdict line of every class is
reproduced character for character" — with no ancestor the freeze is BBX's
own, and the gate's perturbed-copy control is the text's guard); an unknown
class inside a family is `FAIL unknown <family> class` (bbh's shape).
`finding.py` gains no word: `diverged`, `short` (a truth log longer than the
run's — the observation ended early), `unknown-class`, `no-expectation`
already cover the new lines, which is measured by the gate (a new line whose
finding reads `unclassified` is a FAIL of the gate).

**C3 — FAIL-SHORT.** A run log with fewer indices than the truth is `short`,
not `diverged`; the truth comparator says which (a claim set that lost a
document reads short, a wrong value reads diverged).

**C6 — not expressible.** A claim that does not match any declared form is
not "a bit like the `has` form": it is UNBINDABLE with reason `no-form` and
counted in the denominator, never bound by a looser regex.

**RO1 — coverage as a number.** The suite prints, for a document-set run,
`NOTE: coverage <bound+paraphrase>/<claims seen>` at column 0 — the screen's
existing key (readout.py:42) — plus `NOTE: paraphrase <n>` and
`NOTE: unbindable <n>` (listed on the screen as notes, since bbx-3). The
denominator is the log's `END <n>` (R33): every claim the extractors found
in the declared forms plus every listed unbindable one, NOT a ruled constant
— VampireSaved's 346 is a consumer's ruling and stays a consumer's.

**RO2.** The driver's header carries the kind's sentence, read by the
readout like every gate's: "prose, reasoning and causal claims are not
asserted; the truth of the artifact itself is not asserted" — and the
fixture's, "no real document set: every expectation here is fixture class".

**BBX-15 — chirality.** The fixture generator refuses to emit a palindromic
value, a symmetric permutation, a record whose `id` equals its reverse, or
two records with the same `weight`; `--check` re-derives the fixture and
diffs, and ALSO asserts the chirality predicates, so a hand edit cannot make
the fixture symmetric.

**BBX-25 — two instances.** The `set` family gets two consumers inside S3
(`claims` inventory and `covered` shrink-only); `schema` has ONE (the TSV
artifact) until S4's JSON output — it stays inside the document-set profile's
table until then and the readout says so; the driver home `$BBX_HOME/drivers`
has one driver until S4's `cli.sh`.

|---|---|---|---|

| the shifted artifact | perturbed-copy | `docset_driver.sh` | the first data row of a copied `records.tsv` deleted: every claim about the deleted record reads `STALE` and every other index is the truth's — the artifact view is keyed by the record's name (D39), so a deletion is a lost reference, not a shift (measured at bbx-8, 2026-09-10: indices 1 and 10 of `01_all`; the plan had predicted a `MISMATCH` at every bound index, SMS's `base+1`, which is what a POSITIONAL view does — S4's question, gotcha G21); the schema comparator, on the same copy, PASSes if `rows >= 11` and FAILS if `rows = 12` — both directions in one perturbation |
