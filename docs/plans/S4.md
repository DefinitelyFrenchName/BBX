## 3. The design, contract by contract

**S1 — the kind profile `command-line`** in `config.py` KINDS, fourth
profile. `instrument_word` "tool"; no `static_needs_env`, no `tier.patterns`
(PORTABLE: sh + python3; every S4 gate but the file census goes in
`gates/portable.txt`); `[suite]`: `scenario_ext = "cli"` (R32, R35),
`driver = "cli"`, `driver_home` the kind-blind `$BBX_HOME/drivers` (D28),
`runs_per_replay` 2 (D29), `hermetic_unset` = the driver family
`CLI_NONDET` `CLI_TIMEOUT` `CLI_KEEP_ENV` (the search path `CLI_PATH` is the
suite's, as `DOCSET_PATH` is the document-set's under D33 — corrected at
bbx-13 before step 1 was built, BBX-19, retraction X17), `rompath_env =
input_env = CLI_PATH`, `log_summary` = `python3 -m bbx.cli summary` (D43's
shape: prints `NOTE: band-fields <n>`, `NOTE: emitted-files <n>`, `NOTE: exit
<n>`; added to the profile with the driver at step 2, as D43 was added to the
document-set profile at S3 step 4); no
`[thresholds]`; `[fingerprint]` kind-blind `file-sha1` with `file_pattern =
"{set}.py"` for the fixture (the program key is the TOOL's SHA-1, the
whole-set key `dir_sha1` over the tool's directory — a changed tool is an
unregistered identity before any scenario runs, `[BBH-67]`); `[expectations].kinds`
= the kind-blind three plus the four of E1.

**S2 — identity.** For the fixture, `file-sha1` as above. For BBX-as-subject
(R14), `command`: `program_command` = the tree hash of `bin`, `lib` and
`drivers` at HEAD (`git rev-parse HEAD:bin HEAD:lib HEAD:drivers | sha1`),
`wholeset_command` the same plus `gates` — so the key moves exactly when the
harness moves, and a moved key is "unregistered build fingerprint" until the
freeze is reviewed (R38: the refreeze is a step of the close, never automatic).

**S4 — views.** Four, declared in the profile and named by every token:
`stdout`, `stderr`, `exit`, `file` (an emitted file the scenario declares).
The band view is a fifth FILE beside the log (O4), never a change to the log.

**D1–D5 — the driver `drivers/cli.sh`** (sh, calling `lib/py/bbx/cli.py`):
`cli.sh <set> <scenario.cli> <out.log> [sandbox]` (D1). `<set>` names the
tool: `<set>.py` (the fixture) or any executable `<set>` found on `CLI_PATH`
(the driver's own variable; the first directory holding it wins — the
document-set driver's resolver shape, `bbx.cli resolve`). The scenario file
says the arguments, the stdin, the environment the tool may see, the working
directory relative to the sandbox, the files it must emit, and which named
fields are BAND fields. The out file is removed before the run (D5); the
sandbox is the working directory AND `$HOME` AND `$TMPDIR` for the subject
(a fresh `mktemp -d` when omitted, `[BBH-36]`; VampireSaved V-R99, V-R248:
"stage a private HOME for a tool with a hard-coded path"). **The scrub:** the
subject runs under `env -i` with exactly D6's hermetic set (`PATH` pinned,
`LANG`/`LC_ALL` `C.UTF-8`, `HOME`/`TMPDIR` the sandbox,
`PYTHONDONTWRITEBYTECODE=1`) PLUS the scenario's `[env]` table and nothing
from the caller — the caller's environment can no more reach the tool than
it can reach the census commands (D6, G9). `CLI_KEEP_ENV` is REFUSED in S4
(D3: a variable the driver cannot honour is refused, never ignored — the
knob exists so a consumer's need is loud, not silent). Exits (D4): 0 the log
is complete (`END <n>`); 1 the tool is not found or not executable, a
declared emitted file was not produced, stdin could not be fed, the timeout
(`CLI_TIMEOUT`, D-row) elapsed, or the observation is otherwise incomplete —
DISCARDED; 2 the tool DIED BY A SIGNAL (the guard: `END-CRASH <n>` written,
the partial output kept as the bug report — the fixture's `--crash-at`,
bbh's B-X19); 3 `REFUSED: drivers/cli.sh cannot honour <what> (<why>)` — a
scenario key the driver does not know (SMS cliguard, on the scenario
grammar), `CLI_KEEP_ENV`, any of the frame-driven or document-set families
in the environment. **A non-zero exit of the TOOL is not a driver failure:
it is an observation** (the `exit` point), so a tool that refuses an unknown
option (exit 2 and a message) compares PASS against a truth that expects
exactly that — cliguard's lesson as a green scenario, and a crash apart from
a refusal by construction (BBX-4's spirit: two findings, two reports).
`docs/generality.md`'s kind-B row says "`--crash-at n` → exit 1, discarded";
D4 and bins B-X19 say exit 2 with the observation as the bug report. The
plan recommends D4 (R35) and the generality page is corrected in its own
commit when R35 is answered (BBX-19; a retraction row).

**The scenario file `<name>.cli`** (R35): a TOML-subset file — `[scenario]`
with `args = [...]` (one string per argv element, never a shell line),
`stdin = [...]` (one string per line, each newline-terminated — a basic
string holds no `\n` under the subset; corrected at bbx-13, BBX-19, X19) or
`stdin_file = "…"` (relative to the scenario file's directory),
`cwd = "."` (relative to the sandbox), `emits = ["report.json"]` (files the
tool must produce in the sandbox; each is a `file` point), `bands = ["size"]`
(named fields of a structured stdout whose VALUE is judged by the band kind),
`fields = "json"` (the structured-output reader: absent → stdout is lines);
`[env]` one key per variable the tool may see. An unknown key is REFUSED.
Nothing in the scenario states an expected value (§3.4).

**O1 — the observation grammar** (R31: an integer index into the scenario's
own inventory): `0 exit:<n>` first (the exit status is its own line —
`docs/generality.md` kind B); then `<i> line:<sha1>` per stdout line, or,
under `fields = "json"`, `<i> field:<name>:<sha1-of-value>` per key in SORTED
key order (the scenario's inventory is the key list; a band field's token is
`field:<name>:band`, a constant — its value lives in the band view);
`<i> err:<sha1>` per stderr line; `<i> file:<name>:<sha1>` per declared
emitted file; `END <n>`. Every token is one space-free field split in one
place (`bbx.cli`), by field name. `<out>.bands` is the band view:
`<i> <name>=<value>` per band field, `END <n>` — the file the band
comparator reads (O4, BBX-16).

**O5 — input integrity.** The driver records into the sandbox what it fed
(`argv.txt`, `stdin.bin`, `env.txt` — the resolved environment after the
scrub) and the gate asserts they equal the scenario; the must-fire is the
env-scrub control (§5).

**O6 — twice.** Every scenario runs twice (D29); the fixture's `--nondet`
mixes the clock into a line — the NONDETERMINISTIC control; `CLI_NONDET=1`
does the same on the DRIVER's side (a wrapper driver, never the caller's
environment: X11).

**E1 — the kinds** added to the `command-line` profile's table:

| kind (extension) | family | disposition | what it freezes | spec |
|---|---|---|---|---|
| `truth` | `exact` | EVAL | the expected observation log, by index — written by the fixture generator from the DESIGN (`fixture`), or by a consumer from a reference | `exact <baseset>`; the pairing `logs/<scenario>.log` — `compare_exact.py` UNCHANGED (its second consumer) |
| `unordered` | `set` | EVAL | the multiset of stdout lines of an `--unordered` run, both ways (E5) — `compare_set.py`'s inventory mode, its second consumer | `multiset <baseset> inventory`, then one bare table per row (`line`, `sha1`) |

**D7 — the adapters, two frameworks (R37).** `drivers/unittest.sh` and
`drivers/gates.sh`, each a driver of this kind over the SAME `bbx.cli`
(sandbox, scrub, timeout, the log writer) — the generic core has three
consumers at the end of the slice, which is BBX-25 with one to spare.
`unittest.sh <set> <scenario.cli> <out> [sandbox]`: `<set>` is a directory
holding a unittest package; the scenario's `args` are the module names; the
driver runs `python3 -m unittest -v <modules>` in the sandbox under the scrub
and maps every `<case> (<module.Class>) ... <verdict>` line, in order, to
`<i> case:<verdict>:<sha1-of-case-name>`; `Ran <n> tests` is `END <n>`, and a
count that differs from the lines seen is exit 1; `Ran 0 tests` is exit 1
(BBX-7: a green over nothing is DISCARDED, never a PASS). `gates.sh`: `<set>`
is a directory holding a consumer config; the driver runs `bin/bbx run-static
--config <set>/bbx.toml --log <sandbox>/run` and maps every row of the kept
`results.tsv` (by column name) to `<i> gate:<verdict>:<sha1-of-gate-name>`,
`END <n>` = the rows; a MISSING row is a verdict like any other. **The
framework's verdict is an OBSERVATION, never a BBX verdict** (D7): a failing
test is `case:FAIL:…` and compares PASS against a truth that expects it —
the control that the adapter reports what ran, not whether it was good.

**R14 — BBX's own runners as subjects.** The gates adapter's set is
`fixture/selfgates/`: a synthetic consumer (F13a's shape — stub gates that
pass, skip, fail, one MISSING, one unregistered) whose `bbx.toml` is a
`self`-kind config; its scenarios drive `bin/bbx-run-static` and
`bin/bbx-run-sweep --list` (through `bbx run-static` / `bbx run-sweep`, so
the DISPATCHER is executed too). The identity is R38's `command` key. This is
what moves the census's "+kernel" rows: after S4 the two runners and the
dispatcher are executed by a gate of the command-line kind, and the census
gate (R39) asserts it.

**RO1, RO2.** The suite prints `NOTE: band-fields <n>` (the inventory watch,

## 9. What this plan does NOT decide

A framework that is not on the host (pytest, bats, node's runner: R37
declines them, a consumer adds a third adapter under the same core); a tool
that reads a terminal, a signal, or the clock by contract (R5: admitted with
BBX-14 reported unmet); a non-UTF-8 or binary stdout (hashed as bytes — the
`line` point is a line only for text; the design says bytes are one `file`
point and a consumer's question); a subject whose emitted files are a TREE
(`emits` names files, never directories); the mapped-state comparator
(BBX-25); BBX's own `docs/` as a document-set consumer (S3 §9, unchanged);
executable controls (R29, S6); the platform rows (R21); whether a band may
ever be widened WITH a ruling but without a named mechanism (R36 says the
ruling row names the mechanism, and the gate cannot check that it does —
stated as NOT-ASSERTED).
